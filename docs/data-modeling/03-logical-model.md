# 03 — Logical model

Third step of the design process. Maps the [conceptual model](02-conceptual-model.md) to relational
structures: tables, columns, primary keys and foreign keys. Still independent of PostgreSQL-specific
details (exact types, indexes), which belong to the physical model.

## Mapping rules

| Conceptual | Logical |
|---|---|
| Entity | Table |
| Simple attribute | Column |
| Composite attribute (position: x, y) | One column per part (`position_x`, `position_y`) |
| 1:N relationship | Foreign key on the N side |
| 1:N self-relationship | Foreign key to the same table, nullable for roots (`parent_id`) |
| Multivalued attribute (properties) | See "Card properties" |

## Primary keys

**Every table uses an artificial primary key: a UUID version 7** (time-ordered UUID).

- Natural keys (email, category name) change over time; as primary keys, every change would ripple
  through all foreign keys pointing at them.
- Sequential integers leak information (guessable ids, row counts), can only be generated by the
  database, and collide across the tools of the ecosystem.
- UUIDs are unique across every system, unguessable, and can be generated anywhere (API, browser,
  other services) before the row is saved.
- Version 7 starts with a timestamp, so new keys arrive in order and index inserts stay efficient,
  unlike fully random version 4 UUIDs. Generated natively by PostgreSQL 18 (`uuidv7()`) and .NET
  (`Guid.CreateVersion7()`).

Natural keys remain as **unique constraints** (candidate keys):

- `users.email` is unique.
- `(categories.user_id, categories.name)` is unique.

## Naming

Table and column names are English, `snake_case`, and tables are plural (`users`, `categories`, `cards`).
Plural names avoid SQL reserved words such as `user` and `order`, which would need quoting in every query.

## Card properties

Properties are stored in a **`properties` JSON column** on `cards`: one JSON object whose keys are
property keys from the catalog and whose values are the property values.

```json
{ "due_on": "2026-09-30", "done": false }
```

- **Flexible:** adding a property to the catalog needs no database migration.
- **Still queryable:** PostgreSQL understands JSON internally (`properties @> '{"due_on": "2026-09-30"}'`)
  and can index it.
- **Integrity moves to the API:** the database does not check property types. The API validates every
  property against the catalog before writing, and the catalog is described in the OpenAPI contract so
  other systems know what to expect. Frontend validation is a convenience for the user, never the guarantee:
  other tools write through the API without going through the Angular app.
- **Rejected — one column per property:** every new property would need a migration, and user-defined
  properties would be impossible.
- **Rejected — key/value table (EAV):** values lose their types and simple filters become chains of
  self-joins.
- **Ready for user-defined properties:** when users can create their own properties, a property-definition
  table is added and its ids become keys in the same JSON object.

### Catalog (v1)

| Key | Type | Meaning |
|---|---|---|
| `due_on` | date (`YYYY-MM-DD`) | Deadline: the day by which the card must be done. |
| `done` | boolean | Whether the card is finished. |

## Tables

```
users
  id            PK
  name
  email         UNIQUE
  created_at
  updated_at

categories
  id            PK
  user_id       FK → users.id
  name
  sort_order
  created_at
  updated_at
  UNIQUE (user_id, name)

cards
  id            PK
  category_id   FK → categories.id
  parent_id     FK → cards.id   (empty for cards at the root of the category's board)
  title
  color
  position_x
  position_y
  layer
  content       (optional; Tiptap JSON document)
  properties    (JSON object; empty object when the card has no properties)
  created_at
  updated_at
```

## Normalization

A **functional dependency** `A → B` means that knowing `A` determines `B` unambiguously. Normal forms
check that every column depends on the key, the whole key, and nothing but the key.

- **1NF — one value per cell.** Position is split into `position_x` and `position_y`. `content` is treated
  by the database as a single value: stored and read whole, never queried inside.
  **Exception:** `properties` is a multivalued attribute stored in one column and *is* queried inside. This
  is a deliberate deviation, justified by the flexibility of the catalog and supported natively by
  PostgreSQL's JSON type. If a property ever needs strict database-level integrity (types, foreign keys),
  it should move to a regular column.
- **2NF — depend on the whole key.** Automatically satisfied: every primary key is a single column.
- **3NF — depend on nothing but the key.** `users` and `categories` comply.
  **Exception:** in `cards`, for cards with a parent, `id → parent_id → category_id` is a transitive
  dependency: the category is determined by the parent. This is the deliberate redundancy described in the
  conceptual model, protected by the "same category as the parent" constraint.
